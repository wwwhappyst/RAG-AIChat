# 05.2 LLM 流式输出：更早看到答案

## 本阶段做什么

本阶段把最终 LLM 调用从同步等待完整响应，改为 Chat Completions 流式输出。

前端表现是：

```text
检索证据 -> 构造 Prompt -> DashScope LLM 流式返回答案片段 -> 页面逐步显示
```

流结束后，系统仍然会得到完整答案、token usage、召回证据和流程日志。
如果 OpenAI 兼容服务不支持在流式响应中返回 usage，系统会自动退化为“只流式返回答案”，
此时 token usage 可能为空，但不会影响答案展示。

## 为什么要这么做

同步调用时，用户必须等模型完整生成后，页面才显示答案。
流式调用时，模型一开始生成文本，前端就能收到第一个片段。

这主要优化：

```text
首字等待时间
页面体感速度
长回答时的等待焦虑
```

它不一定减少模型总耗时，也不会减少模型需要生成的 token。
如果答案本身很长，模型仍然要完整生成，只是用户不用一直看空白页面。

## 当前实现方式

`src/generator.py` 中新增：

```text
generate_stream(prompt)
```

它会逐步产出：

```text
answer_delta：本次新增文本片段
result：流结束后的完整 GenerationResult
```

`src/pipeline.py` 中新增：

```text
ask_stream(...)
```

它先完成检索和 Prompt 构造，然后把 LLM 的流式片段继续交给前端。

`app.py` 使用 Streamlit 的：

```text
st.write_stream(...)
```

把增量答案直接写到“最终答案”页。

## 流式耗时怎么看

流程日志中会出现新的节点：

```text
DashScope 流式首块等待
DashScope 流式响应接收
LLM 回答文本拼接
```

含义如下：

- `DashScope 流式首块等待`：从发起请求到收到第一个流式响应块的时间，更接近用户体感的首字等待。
- `DashScope 流式响应接收`：持续接收增量文本直到模型完成回答的时间。
- `LLM 回答文本拼接`：把多个 delta 片段合并成完整答案，供证据和调试区使用。
