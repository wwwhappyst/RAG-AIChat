# 05.1 查询向量缓存与并行检索：减少检索等待时间

## 本阶段做什么

本阶段是在第 5 阶段 BM25 和混合检索基础上的性能优化。

新增两项能力：

1. 查询向量缓存  
   相同问题在相同 embedding 模型和维度下，复用本地缓存的 query vector。

2. 混合检索并行 BM25  
   hybrid 模式下，BM25 本地检索和 FAISS 查询向量化同时执行。

3. BM25 分词器预热  
   加载 BM25Store 时提前触发 jieba 词典加载，避免第一次提问时把冷启动时间算进 BM25 检索。

## 为什么要这么做

在线 RAG 问答里，FAISS 和 BM25 本地检索都很快，通常是毫秒级。
真正容易慢的是查询向量化，因为它需要调用 DashScope embedding 远程 API。

典型耗时结构如下：

```text
查询向量化：几百毫秒到一两秒
FAISS 向量检索：通常小于几毫秒
BM25 关键词检索：通常几毫秒
```

所以优化重点不是让 FAISS 更快，而是减少或隐藏 embedding 调用等待。

## 查询向量缓存怎么工作

缓存文件位置：

```text
indexes/query_cache/query_vectors.jsonl
```

每条缓存记录包含：

```text
key
query
model
dimension
vector
created_at
```

cache key 使用以下信息生成：

```text
embedding 模型名称 + embedding 维度 + 规范化后的用户问题
```

这样做是为了避免未来更换 embedding 模型后误用旧向量。
不同模型生成的向量空间不一定相同，不能混用。

## 为什么缓存只用于查询向量

知识库文档向量已经在第 2 阶段离线构建并保存到 FAISS。
在线提问时，每次新增的不确定部分只有用户问题。

所以当前缓存目标是：

```text
用户问题 -> query vector
```

重复问题命中缓存后，可以跳过 DashScope embedding 调用，直接进入 FAISS 检索。

## 混合检索为什么可以并行

hybrid 模式需要两路结果：

```text
FAISS：用户问题 -> query vector -> 向量检索
BM25：用户问题 -> 分词 -> 关键词检索
```

BM25 不依赖 query vector，也不调用 AI API。
因此它可以在等待 DashScope embedding 的同时先执行。

优化前：

```text
查询向量化 -> FAISS 检索 -> BM25 检索 -> 混合合并
```

优化后：

```text
查询向量化 -> FAISS 检索
BM25 检索  ----------------^
两路结果完成后 -> 混合合并
```

因为 BM25 通常只有几毫秒，所以并行带来的收益不会像缓存那么大。
但这个改动能减少不必要的串行等待，也更接近真实检索系统的并行执行方式。

## 为什么有时 BM25 会突然变慢

BM25 检索本身通常是毫秒级，但中文查询进入 BM25 前需要先用 jieba 分词。
jieba 第一次分词时会懒加载词典，这个冷启动可能花几百毫秒。

如果刚重启 Streamlit，第一次查询可能看到：

```text
BM25 关键词检索：几百毫秒
```

之后再次查询会恢复到：

```text
BM25 关键词检索：几毫秒或更低
```

当前代码在 `Bm25Store` 加载时会先做一次短文本分词预热。
这样词典加载成本会发生在 Pipeline 初始化阶段，而不是用户第一次提问的 BM25 计时里。

## 前端耗时怎么看

流程执行时间中，`查询向量化` 的类型会出现两种情况：

```text
DashScope embedding 调用
本地缓存
```

如果显示 `本地缓存`，说明本次没有调用 DashScope embedding。

hybrid 模式下，`检索阶段总耗时` 可能小于各子节点耗时的简单相加。
这是正常现象，因为 BM25 和查询向量化存在并行重叠。
